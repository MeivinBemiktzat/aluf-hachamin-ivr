# אלוף החמין – משחק IVR לימות המשיח

מערכת משחק טלפונית מרובת משתתפים, Node.js על Vercel, שמירת מצב ב-Hugging Face Storage Buckets (S3 API).

## מצב הפיתוח

המאגר נוצר כפרויקט עצמאי. מאגר `monopol-ivr` נבדק לצורך למידת מבנה ה-IVR, זיהוי פרמטרי הקלט, טיפול ב-`read=`, תורים, קודי משחק ושכבת Hugging Face. **לא בוצעו בו שינויים.**

הגרסה הראשונית כוללת:
- שלד API לימות המשיח ותהליך יצירה/הצטרפות באמצעות קוד בן 3 ספרות.
- הקלדת שמות במקלדת עברית.
- מצב משחק אנושי ומצב מול בוטים (הבוטים עדיין דורשים השלמת אסטרטגיה).
- קטלוג מתכונים, מצרכים, קלפי שוק וקלפי חבר'ה.
- מנוע משחק בסיסי ומבחני יחידה.
- מתאם אחסון S3 ל-Hugging Face עם כתיבה מותנית ETag.

**חשוב:** זו נקודת פתיחה לפיתוח ובדיקות, לא גרסת Production. יש להשלים ולבדוק לפני שימוש אמיתי: סבב הצעות סודי לכל השחקנים (כרגע תור ההצעות ומנגנון ההמתנה בסיסיים), הפעלת קלפי חבר'ה מלאה, אסטרטגיית בוטים, תיקו במכרז, כללי חלוקת/צריכת קלפי כסף מדויקים, הגבלת זמן לתור, reconnect, בדיקות עומס ואימות פרוטוקול מול קו בדיקה. אין להציג את המשחק כשלם עד השלמת אלה.

## 1. פריסה ל-GitHub ול-Vercel

1. המאגר: https://github.com/MeivinBemiktzat/aluf-hachamin-ivr
2. חברו אותו לפרויקט חדש ב-Vercel.
3. Framework Preset: **Other**.
4. Root Directory: `./`.
5. Build Command: להשאיר ריק (אין שלב build).
6. Install Command: ברירת המחדל של Vercel (`npm install`).
7. Output Directory: להשאיר ריק.
8. פרסו לאחר הגדרת משתני הסביבה.

## 2. Hugging Face Storage Buckets

צרו Storage Bucket בחשבון Hugging Face והנפיקו S3-compatible credentials עבורו. יש להגדיר ב-Vercel → Project → Settings → Environment Variables:

| משתנה | ערך |
|---|---|
| `HF_NAMESPACE` | שם המשתמש או הארגון ב-Hugging Face שהוא בעל ה-Bucket |
| `HF_BUCKET` | שם ה-Storage Bucket |
| `HF_S3_ACCESS_KEY_ID` | מפתח S3 שהונפק ל-Bucket |
| `HF_S3_SECRET_ACCESS_KEY` | סוד S3 התואם |

הגדירו את כולם עבור Production וגם Preview אם בודקים Preview. אין להכניס מפתחות לקוד, לקובצי JSON, או ל-GitHub. לאחר שינוי משתנים יש לבצע Redeploy.

הקוד משתמש ב-endpoint:
`https://s3.hf.co/<namespace>`
ובמפתחות תחת הקידומת:
`aluf-hachamin/`

כל משחק נשמר כאובייקט JSON עם TTL של שמונה שעות. TTL נבדק באפליקציה; הוא אינו מבטיח מחיקה פיזית מה-Bucket.

## 3. הגדרת שלוחת ימות המשיח

צרו שלוחה מסוג API והגדירו ב-`ext.ini`:

```ini
type=api
api_link=https://YOUR-PROJECT.vercel.app/api/ivr
api_url_post=yes
api_wait_answer_music_on_hold=yes
api_log=yes
```

החליפו את הדומיין בכתובת הפריסה בפועל. לפי תיעוד ימות, `type=api` ו-`api_link` הם ההגדרות הבסיסיות; `api_url_post=yes` בוחר POST. בדקו את ההתנהגות בפועל במערכת שלכם לפני פתיחה לציבור.

### תפריט כניסה
- 1 – משחק חדש.
- 2 – הצטרפות למשחק לפי קוד.

יוצר משחק בוחר משחק אנושי ומספר משתתפים כולל היוצר, או משחק מול בוטים ובוחר מספר בוטים. לאחר מכן כל שחקן מקליד שם במקלדת העברית וממתין עד שהחדר מלא.

## 5. התאמת המשחק

הנתונים שב-`api/game-data.json` הם קטלוג ראשוני שניתן לערוך:
- מתכונים בני 7–8 מצרכים, כולל מתכון צמחוני.
- מצרכים בסיסיים לחמין.
- קלפי שוק לדוגמה, כולל האופה שמעניק קלף חבר'ה לכל השחקנים.
- קלפי חבר'ה ראשוניים שנועדו גם להדגים פעולות חדשות.

הקטלוג אינו תמלול מלא של כל הקלפים המקוריים. לפני הפצה יש להשוות לחפיסת המשחק ולחוברת ההוראות, ולוודא שכל שמות הקלפים וההשפעות מדויקים. קלפים חדשים צריכים להיות מסומנים כקלפי הרחבה מקוריים.

## 6. בדיקות מקומיות

דרישות: Node.js 20 ומעלה.

```bash
npm install
npm test
```

בדיקות טלפון מומלצות:
1. יצירת משחק אנושי עם שני משתתפים.
2. הצטרפות באמצעות קוד תקין, קוד שגוי וחדר מלא.
3. בדיקת שמות בעברית.
4. המתנה עד שכל המשתתפים הצטרפו.
5. משחק מול בוטים – לוודא שכל בוט מקבל תור.
6. בדיקת מכרז עם הצעות שונות, הצעה אפסית והצעה גבוהה מהיתרה.
7. ניתוק וחיוג חוזר.
8. שתי בקשות מקבילות שמשנות אותו משחק – לוודא שאין דריסת מצב.

## 7. מגבלות ותכנון להמשך

- יש להשלים מכרז שבו השרת עובר שחקן-שחקן, אוסף הצעות בסתר, ורק לאחר שכל השחקנים הגישו חושף את התוצאות.
- יש להחליט ולממש כלל שובר שוויון, ולוודא שכל ההצעות משולמות לצדקה גם אם לא זכו.
- כללי קלפי הכסף חייבים לשמור על ערכי הקלפים המקוריים 1–4; אין להניח שאפשר לפרוט קלף באופן חופשי בלי לאשר זאת בחוקים.
- יש לממש קבלת כסף אוטומטית בתחילת פתיחת קלף שוק לשחקן שאין לו כסף: קלף כסף אקראי אחד לכל מצרך שנפתח, כל קלף בשווי 1–4, אלא אם קלף השוק קובע כלל אחר.
- יש לממש פעולות קלפי חבר'ה עם חלונות תזמון ברורים, כולל תגובות במהלך תור של שחקן אחר.
- יש לבנות בוטים אסטרטגיים שיודעים לחשב אילו מצרכים חסרים להם, מה ערך כל הצעה, מתי להשתמש בקלפי חבר'ה ומתי לחסוך כסף.
- יש להוסיף מנגנון anti-stuck ותוקף הצעות כדי שמשחק לא ייתקע כשמשתתף מתנתק.
- אחסון S3 אינו מספק לבדו נעילה טרנזקציונית לכל רצף פעולות. יש להשתמש ב-ETag/conditional write ובטיפול ב-conflict; במקרה התנגשות יש לטעון מחדש ולנסות שוב בצורה מוגבלת.
- אין לבצע retry עיוור לפעולת משחק ששינתה מצב.

## 8. אבטחה ותחזוקה

- כל בקשת API נכתבת ללוג ללא מספר טלפון, שם מלא או קוד גישה.
- אין לשמור סודות בסביבת Git.
- מומלץ להוסיף חתימת בקשה/allow-list לפי האפשרויות הנתמכות בימות לפני Production.
- יש להגביל קצב ניסיונות לקוד משחק ולמנוע ניחוש קודים.
- יש להגדיר מדיניות מחיקה ופרטיות לשמות שחקנים ולנתוני משחק.
- שינויים בנתוני משחק דורשים בדיקות מחדש.

## 9. Rollback

ב-Vercel → Deployments אפשר לקדם פריסה קודמת. נתוני המשחקים נשמרים ב-Bucket בנפרד מהקוד; אין למחוק את ה-Bucket בעת rollback.
